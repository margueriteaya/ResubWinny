# 預覽構圖決定
外部 `mpv.exe` 邊車不是產品需求。 ResubWinny 正在遷移到自己的動態 `libmpv` 用戶端 ABI。 Windows x86_64 運行時被捆綁為可替換的 LGPL 依賴項； macOS 和 Linux 在其平台運行時使用相同的 ABI 合約。

| 後端 | 平台 | 字幕保真度 | 主要權衡 |
| --- | --- | --- | --- |
| `libmpv-render` | Windows/macOS/Linux | 最高;在一個表面上合成影片和 libaribcaption RGBA | 需要 libmpv 整合和本機紋理/表面循環 |
| 多用途乘用車 `overlay-add` | 多用途乘用車平台 | 高低頻 RGBA 幀 | 原始像素上傳和 mpv 版本/VO 限制 |
| 本機視窗覆蓋 | Windows優先 | 高的 | HWND/Z 順序、調整大小、DPI 和平台特定程式碼 |
| WebView圖像層 | 全部 | 適合檔案檢查 | 無法可靠地覆蓋嵌入的本機子窗口 |
| ASS 字幕軌道 | 全部 | 近似 | 遺失精確的 ARIB 字元單元、ruby、DRCS 和背景語意 |

所選的 Windows 路徑是 `libmpv-render`。它將影片和字幕保留在同一個專案擁有的 WGL 表面中，並避免 WebView/本機視窗堆疊問題。當渲染 API 或 WGL 啟動失敗時，`wid` 和 `overlay-add` 用戶端僅保留為每個來源相容性後備。 ResubWinny 不會啟動 `mpv.exe` 或使用 JSON 命名管道。 macOS 和 Linux 將使用相同的字幕模型，但它們的原生渲染表面尚未實現。

類型化的 `get_preview_capabilities` API 公開了此選擇，而不會讓 UI 依賴 Windows 特定的細節。在渲染路由及其用戶端覆寫回退中，Tauri 後端透過鍵入的 `sync_preview_overlay` 作業對 mpv 時間進行取樣，並在上傳之前將傳回的本機字幕平面與先前的平面進行比較。 WebView 可以安排該操作，但不會計算媒體時間、撰寫字幕或實現後備時鐘。因此，未更改的字幕平面不會導致另一次原始像素 IPC 傳輸；這可以限制長而稀疏的錄音，而無需預先載入字幕時間軸。更改後的 RGBA 平面將寫入每個預覽的臨時 BGRA 文件，並與其記錄的 `overlay-add` 文件/偏移參數一起傳遞到 mpv；預覽停止時臨時文件將被刪除。 Tauri 存檔閱讀器保留只向前的遊標和最多 128 個活動間隔；向後查找會重置有界遊標，因此它永遠不會將多小時的時間線加載到內存中。 mpv時間查詢的逾時時間很短；當 IPC 未準備好時，後端返回 `awaiting-player-time` 並將最後一個平面保留在適當的位置，而不是發明本地時鐘時間軸。

`get_preview_runtime` 報告載入的運行時路徑以及該運行時是否會匯出 libmpv 渲染 API。在Windows上，完整的渲染API預設選擇本機渲染路由；如果特定來源無法初始化該路由，則該預覽會安全地回退到客戶端覆蓋路由。專用的本機執行緒擁有專案擁有的 WGL 上下文、`vo=libmpv` 實例和渲染上下文。它在 `loadfile` 之前創建渲染上下文，處理有界控制/調整大小/時間訊息，每 16 毫秒最多泵送一次掛起幀，呈現在預設幀緩衝區上，並在相同的 WGL 上下文保持當前狀態時釋放上下文。這將脆弱的 ABI/生命週期和線程排序保留在後端內。

相同渲染線程僅接受後端組成的 BGRA 字幕平面。當平面發生變化時，它會上傳有界的 OpenGL 紋理，並在 mpv 視訊幀之後混合該紋理； WebView 從不接收視訊幀或執行標題佈局。它向 libmpv 詢問其顯示正確的視頻方面，並將字幕平面映射到生成的信箱/柱箱視口；如果媒體參數尚未準備好，它會安全地回落到整個表面並重試。一旦運行時公開完整的渲染 API，Windows 路由就可以透過類型化功能合約來取得。它請求 `hwdec=auto-safe`，然後報告 libmpv 的實際 `hwdec-current` 選擇（如果可用）。這可能使用相容的回拷貝加速，但不是零拷貝 D3D/ANGLE 硬體解碼聲明。下面介紹的真實語料庫Windows 4K長門就完成了。獨立的 2K/8K 門、參考螢幕截圖比較和 DPI 審查仍然是發布品質的工作，而不是隱藏的後備工作。

`scripts/validate-preview.ps1`是Windows原生的煙門。它使用透過 `ARIB_FIXTURE_DIR` 提供的合法本地記錄，創建一個真正的 WGL 主機，加載捆綁的 libmpv 運行時，啟動專用渲染工作器，並需要一個非均勻解碼視頻幀緩衝區以及一個後端 RGBA 字幕紋理上傳和清除，而不會出現工作器錯誤。它在同一渲染線程上捕獲 WGL 後台緩衝區，並斷言捕獲的 RGBA 像素中存在上傳的不透明綠色測試紋理。 `bs4k_test_2.ts` 煙霧於 2026 年 7 月 29 日過去。這將驗證生命週期、TS 開啟、解碼影片、本機呈現、紋理混合和有界幀緩衝區讀回。煙霧使用 3840×2160 HEVC 源，捕捉 1920×1080 的混合平面，然後將原始表面大小調整為 3840×2160，並需要保留尺寸和可測量的呈現節奏。這是一個 Windows 路由回歸閘門，而不是 8K 吞吐量或零拷貝解碼的聲明。參考螢幕截圖擷取、應用程式 DPI 審核和影像差異批准仍然是獨立的。

透過 `-Long` 會增加 120 秒 4K 播放閘限。它運行相同的進程內本機路徑，保持 3840x2160 表面活動，執行三個完整的 1920x1080 字幕平面替換，並執行暫停、恢復、精確搜尋和有界關閉。預設門閾值為至少 20 呈現幀/秒、最多 10 秒啟動、1 秒控制/字幕更新延遲、3 秒關閉、2048 MiB 絕對工作集以及預熱 4K 基線後 512 MiB 增長。結果以架構版本化 JSON 形式寫入 `build/validation/` 下面。

2026 年 7 月 30 日，與真實 3840x2160 HEVC `bs4k_test_2.ts` 的運行，使用 `d3d11va-copy` 在 120 秒內維持 34.74 呈現幀/秒，在 1.69 秒內開始，峰值為 1526. MiB，最多上傳了完整的字幕平面34.6 毫秒，最多 14.7 毫秒完成控制，並在 337 毫秒內停止，沒有渲染錯誤。這些是針對此 Windows 電腦的回歸測量，而不是超出明確的通過/失敗閾值的通用硬體要求。該工具使用 Cargo 的測試配置文件，而捆綁的 libmpv 二進位檔案、WGL 表面、解碼器和組合路由與應用程式使用的本機運行時相同；打包發布重新運行仍然是一個單獨的工件接受步驟。
