# 預覽合成方案決定
外部 `mpv.exe` 旁掛行程不是產品需求。ResubWinny 正在遷移到自己的動態 `libmpv` 用戶端 ABI。Windows x86_64 執行時以可替換的 LGPL 依賴項形式捆綁；macOS 與 Linux 使用各自平台執行時，遵循同一套 ABI 合約。

| 後端 | 平台 | 字幕保真度 | 主要權衡 |
| --- | --- | --- | --- |
| `libmpv-render` | Windows/macOS/Linux | 最高；在同一個表面上合成影片與 libaribcaption RGBA | 需要 libmpv 整合和本機紋理/表面迴圈 |
| mpv `overlay-add` | mpv 支援的平台 | 對低頻 RGBA 影格保真度高 | 原始像素上傳和 mpv 版本/VO 限制 |
| 本機視窗覆蓋層 | Windows 優先 | 高 | HWND/Z 順序、調整大小、DPI 和平台特定程式碼 |
| WebView 圖像層 | 全部 | 適合檔案檢查 | 無法可靠地覆蓋嵌入的本機子視窗 |
| ASS 字幕軌道 | 全部 | 近似 | 遺失精確的 ARIB 字元單元、ruby、DRCS 和背景語意 |

所選的 Windows 路徑是 `libmpv-render`。它把影片與字幕保持在同一個由專案自己持有的 WGL 表面上，避免 WebView 與本機視窗的層疊問題。只有在渲染 API 或 WGL 啟動失敗時，`wid` 加 `overlay-add` 的用戶端路徑才作為按來源生效的相容性後備保留。ResubWinny 不會啟動 `mpv.exe`，也不使用 JSON 具名管道。macOS 與 Linux 將採用同一套字幕模型，但其本機渲染表面尚未實作。

類型化的 `get_preview_capabilities` API 對外暴露這一選擇，而不讓 UI 依賴 Windows 特定細節。無論走渲染路徑還是其用戶端覆蓋層後備，Tauri 後端都透過類型化的 `sync_preview_overlay` 操作取樣 mpv 時間，並在上傳之前把回傳的本機字幕平面與上一個平面作比較。WebView 可以排程該操作，但不計算媒體時間、不合成字幕、也不實作後備時鐘。因此，未發生變化的字幕平面不會觸發又一次原始像素 IPC 傳輸；這樣，長而稀疏的錄影也能保持有界，無需預先載入其字幕時間軸。發生變化的 RGBA 平面會寫入每次預覽各自的暫存 BGRA 檔案，並按 mpv 已記錄的 `overlay-add` 檔案/位移參數傳給它；預覽停止時刪除該暫存檔案。Tauri 的檔案讀取器只保留單向前進的游標和至多 128 個活動區間；向後跳轉會重設這個有界游標，因此它絕不會把長達數小時的時間軸載入記憶體。mpv 時間查詢的逾時很短；當 IPC 尚未就緒時，後端回傳 `awaiting-player-time` 並讓上一個平面留在原處，而不是憑本機時鐘編造一條時間軸。

`get_preview_runtime` 報告已載入的執行時路徑，以及該執行時是否匯出 libmpv 渲染 API。在 Windows 上，若渲染 API 完整，則預設選擇本機渲染路徑；若某個來源無法初始化該路徑，該次預覽會安全回落到用戶端覆蓋層路徑。一個專用的本機執行緒持有由專案自己建立的 WGL 上下文、`vo=libmpv` 實例與渲染上下文。它在 `loadfile` 之前建立渲染上下文，處理有界的控制/調整大小/時間訊息，對待處理影格至多每 16 毫秒泵送一次，在預設影格緩衝區上呈現，並在同一個 WGL 上下文仍為當前上下文時釋放渲染上下文。這樣，脆弱的 ABI 生命週期與執行緒順序都被收在後端內部。

同一渲染執行緒只接受後端合成的 BGRA 字幕平面。平面發生變化時，它上傳有界的 OpenGL 紋理，並在 mpv 影片影格之後混合該紋理；WebView 從不接收影片影格，也不執行字幕版面配置。它向 libmpv 查詢顯示正確的影片長寬比，並把字幕平面映射到由此得到的、排除上下或左右黑邊的視訊內容檢視區；若媒體參數尚未就緒，則安全回落到整個表面並重試。一旦執行時暴露完整的渲染 API，Windows 路徑即可透過類型化能力合約取得。它請求 `hwdec=auto-safe`，隨後在可得時報告 libmpv 實際選定的 `hwdec-current`。這可能使用相容的回拷（copy-back）加速，但不構成零拷貝 D3D/ANGLE 硬體解碼的聲明。下文描述的真實語料 Windows 4K 長時閘門已完成。獨立的 2K/8K 閘門、參考截圖比對與 DPI 審查仍屬發布品質工作，而不是隱藏的後備路徑。

`scripts/validate-preview.ps1` 是 Windows 原生路徑的冒煙閘門。它使用透過 `ARIB_FIXTURE_DIR` 提供的合法本機錄影，建立真實的 WGL 宿主，載入捆綁的 libmpv 執行時，啟動專用渲染 Worker，並要求得到一個非均勻的解碼影片影格緩衝區，以及一次後端 RGBA 字幕紋理的上傳與清除，且過程中不出現 Worker 錯誤。它在同一渲染執行緒上抓取 WGL 後台緩衝區，並斷言上傳的不透明綠色測試紋理確實出現在抓取到的 RGBA 像素中。`bs4k_test_2.ts` 冒煙測試於 2026 年 7 月 29 日通過。該閘門驗證生命週期、TS 開啟、影片解碼、本機呈現、紋理混合與有界影格緩衝區回讀。冒煙測試使用 3840×2160 HEVC 源，在 1920×1080 上抓取混合後的平面，隨後將本機表面調整為 3840×2160，並要求尺寸得到保留且呈現節奏可測量。這是 Windows 路徑的迴歸閘門，不構成 8K 吞吐量或零拷貝解碼的聲明。參考截圖抓取、應用程式 DPI 審查與影像差異審批仍是各自獨立的閘門。

傳入 `-Long` 會追加一道帶閾值的 120 秒 4K 播放閘門。它執行同一條行程內本機路徑，保持 3840x2160 表面處於活動狀態，執行三次完整的 1920x1080 字幕平面替換，並演練暫停、恢復、精確跳轉與有界關閉。預設閘門閾值為：呈現影格率至少 20 影格/秒，啟動至多 10 秒，控制/字幕更新延遲至多 1 秒，關閉至多 3 秒，絕對工作集至多 2048 MiB，且在 4K 基線預熱之後成長至多 512 MiB。結果以帶 schema 版本的 JSON 寫入 `build/validation/` 下。

2026 年 7 月 30 日針對真實 3840x2160 HEVC `bs4k_test_2.ts` 的一次執行，使用 `d3d11va-copy`，在 120 秒內維持 34.74 呈現影格/秒，啟動耗時 1.69 秒，工作集峰值 1526.9 MiB，預熱之後成長 111.9 MiB，上傳一次完整字幕平面至多耗時 34.6 毫秒，控制操作至多耗時 14.7 毫秒，並在 337 毫秒內停止，未出現渲染錯誤。這些是這台 Windows 機器上的迴歸測量值，除明確的通過/失敗閾值之外，不構成普適的硬體要求。該測試裝置使用 Cargo 的 test 設定，而捆綁的 libmpv 二進位、WGL 表面、解碼器與合成路徑都與應用程式實際使用的本機執行時一致；在打包發布版本上重跑仍是獨立的產物驗收步驟。
