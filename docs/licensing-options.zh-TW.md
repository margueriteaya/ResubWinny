# ResubWinny 授權條款選項

這是一份工程相容性審查，不構成法律意見。儲存庫所有者於 2026-07-27 為 ResubWinny 選擇 MPL-2.0。下列替代方案作為決策歷史保留，而非目前有效的授權條款選擇。

## 已選擇：MPL-2.0

MPL-2.0 在原始碼檔案層面施加 copyleft。散佈者可以將 ResubWinny 與更大的專有產品結合，但對 MPL 涵蓋檔案的修改必須繼續以 MPL-2.0 提供。這符合專案既定目標：防止字幕核心的改進只以不透明二進位形式迴流，同時不要求每個呼叫 Worker 的程式採用同一授權條款。

Rust Worker、Tauri 服務和 Svelte 應用使用同一授權條款。保留有版本的 Worker 協定和 CLI，以供使用其他授權條款的工具使用。權威根目錄 `LICENSE` 文字和 `license = "MPL-2.0"` 套件中繼資料現已存在。桌面捆綁套件也包含根授權條款。

## 更強的替代方案：GPL-3.0-or-later

GPL-3.0-or-later 要求被散佈的衍生應用在 GPL 下提供其對應原始碼。它對封閉分支提供更強保護，但會顯著增加專有桌面整合，以及某些商店或裝置散佈的難度。僅當這種排除是有意為之時才選擇它。

## 拆分替代方案：LGPL-2.1-or-later 核心，MPL-2.0 桌面端

Worker/核心可以使用 LGPL-2.1-or-later，而 Tauri/Svelte 應用使用 MPL-2.0。若未來對共享核心函式庫進行二進位連結是主要產品目標，這一做法會有用。目前狹窄邊界是程式協定，而非公開共享函式庫；因此拆分會增加貢獻和發行複雜性，卻沒有具體收益。它不是建議的 v0.1 安排。

## 寬鬆替代方案：Apache-2.0 OR MIT

這是最便於嵌入、封裝和企業採用的選項。它允許封閉的修改版分支，因而不符合專案最初的互惠目標。Apache-2.0 增加明確的專利授權；MIT 更短。雙重 `Apache-2.0 OR MIT` 在 Rust 生態中很常見。

## 不建議：Anti 996 License 1.0

Anti 996 License 1.0 不適合作為擬以開源軟體形式散佈專案的有效授權條款。已審查的上游文字將其標為草案，並將使用條件設為遵守多個司法管轄區中最嚴格的適用勞動規則。這些條件是倫理使用限制，而非通常的版權互惠。它們與《開放原始碼定義》的非歧視原則衝突，且該授權條款不在 OSI 批准的授權條款清單中。

它不應與 MPL-2.0 結合：

- `MPL-2.0 OR Anti-996-1.0` 允許每個接收者選擇 MPL-2.0，因此不能執行 Anti-996 條件。
- `MPL-2.0 AND Anti-996-1.0` 會給 MPL 涵蓋檔案增加非標準限制，造成不確定的相容性和執行問題，並且很可能被套件儲存庫和下游散佈者拒絕。

ResubWinny 可在其 README、行為準則或專案治理中宣告對公平勞動實務的支援，而不把該立場變為軟體使用限制。這類宣告必須標識為不具約束力，且不得被表述為 MPL-2.0 授權的一部分。

## 第三方與資產邊界

專案授權條款不替代相依性義務：

- `libaribcaption` 為 MIT，必須保留其版權/授權條款宣告。
- 隨附的 Windows `libmpv-2.dll` 是 LGPL 建置。它必須保持可替換，隨附適用 LGPL 宣告，並為該精確建置提供有效的對應原始碼機制。
- 用於 ARIB 的 Rounded M+ 1m 在 M+ FONT LICENSE 下再散佈。其附加的 WadaLabMaruGo2004ARIB 字形原始碼允許修改、商業使用、捆綁和再散佈，目前上游以公有領域/Unlicense 發布。精確隨附的二進位檔按 SHA-256 與 `5ym/arib-font` 一致。其來源及兩項授權記錄在字型旁的 `third_party/rounded-mplus-1m-arib/` 中，並且必須隨捆綁套件釋出。
- `makeding/aribb62.js` 在套件中繼資料中宣告 MIT，但已審查提交中沒有獨立授權條款檔案。行為參考已有記錄；沒有可再散佈宣告時，不得隨附複製的原始碼。
- 廣播語料檔案不受原始碼授權條款涵蓋。公開測試必須使用可再散佈的構造 fixture、雜湊或獨立授權的摘錄。

公開散佈前，應加入 `THIRD_PARTY_NOTICES.md`，並在每個安裝程式中包含相關第三方宣告。
