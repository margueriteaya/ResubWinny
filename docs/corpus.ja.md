# ローカル放送回帰コーパス

放送録画は意図的にコミットも再配布もしていません。合法的なローカルサンプルを任意のディレクトリに置き、`ARIB_FIXTURE_DIR` をそのディレクトリに設定してください。テストは意図的に暗黙の開発者パスへフォールバックしないため、長時間サンプルの実行では、読み取ろうとしているコーパスが必ず明示されます。

```powershell
$env:ARIB_FIXTURE_DIR = 'C:\tvrecords_testfile'
$env:ARIB_LONG_FIXTURE = '1'
cargo test -p arib-caption-worker decodes_ -- --nocapture
```

これらのオプトイン検査は入力全体をストリーミング処理し、以下の現在のベースラインをアサートします。ソースバイト、字幕、スクリーンショットは公開しません。

このコーパスでは、ユーザーが現実的に入手でき、内容が検証済みの録画を意図的に優先しています。地上波 MPEG-TS サンプルと 192 バイト MPEG-TS/TTML サンプルがリリースゲートです。後者はパケット化された MPEG-TS 録画であり、ネイティブ BS4K TLV をキャプチャした証拠として使用してはなりません。現在、TLV/MMTP には同等のローカルリリースサンプルがありません。合法的な実キャプチャを入手するまでは、そのパーサー、シグナリング上の制限、Raw エビデンスの契約を、有界な構築テストでカバーします。

公開プロトコルサンプルは worker の `synthetic` モジュールから利用できます。`make_ts_packet`、`make_pat`、`make_pmt`、`make_pes`、`make_b24_data_group`、`make_mmtp_packet` は、放送録画を埋め込まず、放送事業者固有のセマンティクスを持つとも主張せずに、パーサーテスト用の決定論的なパケット境界とセクション境界を構築します。

完全スキャンを行わずにリリース成果物をスモークチェックするには、次を実行します。

```powershell
$env:ARIB_FIXTURE_DIR = 'C:\tvrecords_testfile'
.\scripts\validate-corpus.ps1
```

`-Long` を追加すると、2 つの完全な変換が一時検証ディレクトリで実行されます。このスクリプトがコーパスディレクトリに出力を書き込むことはありません。

パーサーのファジングは、リリースワークスペース外の `fuzz/` に置かれています。初期ターゲットは、コンテンツベースの TS/TLV プローブ、strict TTML エンベロープデコード、有界な ARIB SI サービス名テキストデコード、188/192 バイト TS PSI/PES メタデータ解析、MMTP/TLV ペイロードエンベロープをカバーします。`cargo check --manifest-path fuzz/Cargo.toml` は stable ツールチェーンでのコンパイルチェックを提供します。CI ではさらに、Linux nightly 上で `cargo-fuzz` を使用してすべてのターゲットをビルドします。PSI/PES/B24 ステートマシンおよび、より深いシグナリング／MPU セマンティックファジングのターゲットは、今後のコーパス作業として残されています。週次ワークフローでは、宣言済みの各ターゲットを有界な時間間隔で実行します。

表示または形式を変更する場合は、無視対象の検証ディレクトリに出力を作成し、プロジェクトアーカイブ、ASS、TTML、Raw PES エビデンス、未解決の DRCS アセットディレクトリを比較してください。完全なコマンドは次のとおりです。

```powershell
.\build\cargo\release\arib-caption-worker.exe convert `
  "$env:ARIB_FIXTURE_DIR\chijo_digital_test.ts" `
  artifacts\validation\chijo_digital_test.ass --ttml --archive --raw

.\build\cargo\release\arib-caption-worker.exe convert `
  "$env:ARIB_FIXTURE_DIR\bs4k_test.m2ts" `
  artifacts\validation\bs4k_test.ass --ttml --archive --raw
```

M2TS サンプルは特に重要です。その private PES エンベロープには、有効な TTML ドキュメントの前に非 UTF-8 バイトが含まれています。回帰では、トランスポートのフレーミングが UTF-8 でないという理由だけで PES 全体を拒否してはなりません。XML テキスト自体は、宣言されたエンコーディングまたは BOM に厳密に従ってデコードしなければなりません。

Windows ネイティブプレビューのスモークゲートでは B24 `bs4k_test_2.ts` サンプルを使用し、その録画は配布しません。

```powershell
$env:ARIB_FIXTURE_DIR = 'C:\tvrecords_testfile'
.\scripts\validate-preview.ps1 -FixtureDirectory $env:ARIB_FIXTURE_DIR
```

これは、WGL ホストの作成、プロセス内での libmpv 読み込み、レンダー worker の起動、録画のオープン、正常な終了を検証します。これは意図的に視覚的スクリーンショット受け入れ検査とは分離されており、ハードウェアデコードまたはピクセル忠実度の主張として解釈してはなりません。

`-Long` を追加すると、しきい値付きの 120 秒 Windows 4K ゲートを実行できます。

```powershell
.\scripts\validate-preview.ps1 `
  -FixtureDirectory $env:ARIB_FIXTURE_DIR `
  -Long
```

このゲートは 3840x2160 のネイティブサーフェスをアクティブに保ち、完全な 1920x1080 バックエンド字幕プレーンを 3 回置換し、一時停止、再開、正確なシーク、終了を実行します。20 presents/s 未満、起動が 10 s 超、制御または字幕アップロードが 1 s 超、終了が 3 s 超、ワーキングセットが 2048 MiB 超、または 4K ウォームアップ後のワーキングセット増加が 512 MiB 超の場合に失敗します。スキーマバージョン付きの結果は `build/validation/preview-performance-windows-4k.json` に書き込まれます。

2026-07-30 の実コーパスベースラインでは、`d3d11va-copy` を使用して 120 秒間 34.74 presents/s を維持しました。ピークワーキングセットは 1526.9 MiB、ウォームアップ後の増加量は 111.9 MiB でした。これは Windows 4K 長時間ゲートのみを完了したものです。8K、クロスプラットフォーム、DPI、視覚的忠実度の受け入れ結果ではありません。テストハーネス自体は Cargo の test プロファイルを使用し、アプリケーションと同じバンドル済み libmpv DLL およびネイティブ WGL ルートを読み込みます。パッケージ化されたリリースの受け入れ検査は別途追跡されます。

2026-07-31 のパッケージ版 Windows 受け入れ検査では、最終リリース実行ファイルと `bs4k_test_2.ts` を使用しました。コンテンツプローブは 188 バイト MPEG-TS/B24 を選択し、ネイティブ libmpv は初期一時停止中に映像を表示しました。EIT/NIT/TOT から派生したチャンネル、ネットワーク、番組、説明、放送時刻が表示され、PID `0x0130` は 118 デコードイベントを生成しました。ストリーミングアーカイブが `.jsonl.part` から公開用の `.jsonl` パスへ変更された後、タスクタイムラインには実際の字幕バーが再表示され、「アーカイブが見つからない」という診断はありませんでした。これはこのルートのパッケージ回帰結果であり、すべてのデスクトップワークフローの受け入れ結果でも、macOS/Linux プレビューの主張でもありません。

## ストリーミングメモリのリリースゲート

有界パーサー定数は大容量録画に必要なエビデンスですが、それだけでは十分ではありません。リリース候補はさらに、1 GiB 以上の TS/M2TS 変換を少なくとも 1 回完了し、Worker のピークワーキングセットが **384 MiB** 以下でなければなりません。

```powershell
.\scripts\validate-memory.ps1 `
  -Source "$env:ARIB_FIXTURE_DIR\chijo_digital_test.ts" `
  -TrackId 276
```

このスクリプトは絶対ピーク値と、入力 1 GiB あたりのピーク MiB を報告します。絶対値ゲートは、タイムライン／PES 全体を誤って保持する事態を検出します。3 GiB、11 GiB、18 GiB のサンプル間で比率を比較することで、録画時間に比例してメモリが増加しないことを確認できます。生成された出力は隔離された一時ディレクトリに保持され、測定後に削除されます。

2026-07-27 に測定した Windows x86-64 リリースベースライン：

| サンプル | 入力 | ピークワーキングセット | ピーク／入力比率 |
| --- | ---: | ---: | ---: |
| `bs4k_test_2.ts`、PID 0x0130 | 2.877 GiB | 22.5 MiB | 7.83 MiB/GiB |
| `chijo_digital_test.ts`、PID 0x0114 | 17.303 GiB | 35.7 MiB | 2.06 MiB/GiB |

入力サイズが 6 倍になっても、絶対ピーク値の増加はわずか 13.2 MiB でした。これは録画全体の保持ではなく、有界ストリーミング処理と整合します。これらの数値はこのマシンの回帰ベースラインであり、すべてのデコーダー／ランタイムビルドでアロケーターのオーバーヘッドが同一であることを保証するものではありません。
