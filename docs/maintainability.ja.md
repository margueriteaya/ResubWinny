# 保守性レビュー

本書は、現在のエンジニアリング上の境界と、リポジトリをソースの一般公開に適した状態にするまでに必要な残作業を記録します。

## 確立済みの境界

- Svelte アプリケーションは状態を表示し、型付き Tauri ゲートウェイを呼び出します。トランスポートストリームの解析、字幕のデコード、動画フレームの描画は行いません。
- Tauri サービスはデスクトップのライフサイクル、永続化、ネイティブプレビュー、Worker の監督を担当します。メディア解析は引き続き `arib-caption-worker` に置かれます。
- Worker は `CaptionPlane -> RegionInterval -> exporters` を唯一のセマンティック経路として維持し、狭い C ブリッジを介してのみ libaribcaption を使用します。
- 生成ファイルは `build/` 配下に分離されます。ソースビルドは既存の `target/`、`dist/`、またはコミット済みログに依存しません。
- Tauri バンドルの作成では、リリース用 Worker リソースを明示的にビルドします。デスクトップの `cargo check/test/clippy` を直接実行する場合、バンドル専用のリソース検証はスキップされるため、コントリビューターが Rust コードの確認だけのために古いリリース用 Worker を用意する必要はありません。Worker またはその他のバンドル対象リソースがない場合、リリースビルドは引き続き失敗します。
- ResubWinny のソースは MPL-2.0 でライセンスされます。Rust とフロントエンドのパッケージメタデータは同じ SPDX 識別子を宣言し、デスクトップバンドルにはルートの正規ライセンスが含まれます。

## 完了した分割

| 以前のホットスポット | 現在の構造 |
| --- | --- |
| デスクトップ字幕レンダラー | `caption_renderer.rs` は現在、合成の調整を担当し、`layout`、`rich_text`、`style`、`glyph`、`bitmap`、`tests` が個別の関心事を担当します。 |
| デスクトッププレビュー | `preview.rs` は機能検出と安定したネイティブコマンドラッパーを担当し、アーカイブのページング、オーバーレイ同期、Windows ネイティブ再生、非対応プラットフォーム用スタブ、テストは別モジュールです。 |
| デスクトップジョブ | `jobs.rs` は公開タスクモデルを担当し、JSON/JSONL 永続化とキュースーパーバイザーは `jobs/repository.rs` と `jobs/supervisor.rs` に分離されています。 |
| Worker エクスポーター | 公開エクスポーター境界は `exporters/mod.rs` に残り、ASS、TTML、テキスト形式、B24 オーケストレーション、エビデンス、ルビレイアウトは形式別のモジュールに置かれます。 |
| Worker TTML | B62 セマンティクス、厳密な XML 文書デコード、TS/PES スキャンは、それぞれ独立した `ttml`、`document`、`scan` モジュールです。 |
| 実験的 TLV/MMTP | 基本パケット/MPU 処理、シグナリング/MPT、エビデンス書き込み、制約付き経路は別モジュールです。 |
| Worker テスト | コーパス、TS/M2TS、B24/タイムライン、TTML、TLV、アーカイブ、合成プロトコルの各スイートは別ファイルで各自のフィクスチャを所有し、完全なベースラインは 146 テストです。 |
| libmpv | 動的クライアント ABI/再生と Windows 描画 Worker は分離され、描画テストも隔離されています。 |
| デスクトップタイムライン | 公開ページング/表示は `timeline.rs` に残り、上限付きライブウィンドウと追加カーソルの状態は `timeline/cache.rs` に分離されています。 |
| Svelte アプリケーション | テーマ/ロケール設定、マルチタスク調整、DRCS 辞書状態、タスク表示、出力形式メタデータは機能コントローラーへ移されました。マルチタスク、DRCS、設定のビューはソースルートではなく、それぞれを所有する機能ディレクトリ配下に置かれています。 |

残るアプリケーションシェルは明示的なコンポジションルートです。`SourceSession` はソース準備、検査世代、ビジー期間、古い結果/エラーの抑制を担当し、その後、現在のソースに対してのみタスク設定を適用してプレビュー/インデックスを有効化します。`ExportSession` は、古いジョブ作成コールバック、古い失敗、プレビューインデックスのキャンセルを含むエクスポート/インデックス要求の有効性と、それらの開始/成功/失敗状態の投影を担当します。`PreviewSession` はネイティブプレビューのジオメトリ、ライフサイクル、管理された開始/停止遷移、シーク/スクラブの調整、および未知の最初のメディアサンプルと実際のゼロタイムスタンプの区別を担当します。また、リサイズの合流とプレビューページの生成/再開状態も担当するため、古い WebView ホストや型のない再開タイムスタンプがアプリケーションシェルへ漏れません。再生マッピングの永続化と明示的なメディアからプロジェクトへのカーソル再マッピングも、このプレビュー領域内に残り、プレイヤーコマンドと音量の IPC エラー/通知処理も同様です。

検査成功時の既定値は純粋なタスク設定遷移によって生成され、シェルは出力パス、初期トラック/形式選択、ソース通知をフィールド単位で再構築しなくなりました。バッチコントローラーはキューのライフサイクルと編集中項目のトラック投影を担当し、機能横断のタスク有効化はコンポジションルートに残ります。
`HistorySession` は上限付きタスク履歴の永続化を、`LayoutSession` はレスポンシブなシェル遷移を担当します。`runtime-session.ts` はタスク実行時リセット、`feedback-session.ts` は上限付き通知とバックエンドエラーメッセージ、`selection-session.ts` は出力形式・保存・トラック選択の遷移、`bootstrap-session.ts` は独立したデスクトップ起動リソースの読み込み、`application-lifecycle-session.ts` はデスクトップイベント購読と破棄、`recovery-session.ts` はチェックポイントの適格性と再生を一元管理します。これらのセッションは結果を Svelte 値へ投影しますが、第二のグローバルストアにはなりません。

最大の本番ファイルは現在、Worker `exporters/ass.rs`（約 1,185 行）、`caption/ruby.rs`（約 1,080 行）、`App.svelte`（約 1,100 行）、Worker `caption/ttml.rs`（約 764 行）、デスクトップ `jobs/repository.rs`（約 720 行）、フロントエンド `features/batch/BatchQueue.svelte`（約 632 行）です。エクスポーター、ジョブ、プレビューのエントリーモジュールは、実装の寄せ集めではなく、小さな所有権境界になりました。今後の分割は、恣意的な行数しきい値ではなく、ASS イベント構築、ルビの関連付け/レイアウト、アプリケーションセッションのライフサイクル、リポジトリの関心事、マルチタスクのテーブル/プリセットの関心事に従うべきです。

時間領域は、その所有権境界で明示されています。フロントエンドとデスクトップのマッピング層はメディアのミリ秒とプロジェクトのミリ秒を区別し、Worker は 33 ビット MPEG PES クロックを `Pts90k` として表現して、Caption IR、エビデンス、タイムライン処理へ入る時にのみミリ秒へ変換します。MMT プレゼンテーション NTP は独立したトランスポート概念のままです。

Caption IR の収束はトランスポートモデル内ではなく、解析後に行われます。閉じたゼロコピーの `CaptionCueRef` は、B24 `RegionInterval` と ARIB-TTML `TtmlCaption` に共通するタイミング、領域、経路、プレーンテキスト、ルビ数、DRCS 存在性のセマンティクスを公開しつつ、経路固有の DRCS、ルビ、スタイル、来歴ペイロードを完全に保持します。アーカイブライターはこの共通境界を使用しますが、schema-v1 の `region_interval` と `caption` のレコード形状を保持します。

一部のレンダラーホットパス関数は、一時コンテキストオブジェクトの割り当てを避けるため、引き続きジオメトリを明示的に渡します。互換性用の `start_export`、`create_job`、Worker イベントヘルパー、libmpv スレッドエントリーポイントも広いシグネチャを持ちます。これらの lint 例外は局所的で根拠があり、新しい API は型付きの要求/状態オブジェクトを使用すべきです。既存の Tauri パラメーター名は、フロントエンド契約の移行と連携する場合にのみ変更しなければなりません。

## ビルドと品質ゲート

- Worker、デスクトップ crate、fuzz crate の Cargo 出力は `build/cargo/` に統合され、Vite 出力は `build/frontend/` に置かれます。
- `scripts/clean.ps1` は現在の出力に加え、廃止されたルート、fuzz、Vite、Tauri の出力場所を削除します。`-Dependencies` は `node_modules` も削除します。
- Worker とデスクトップの Clippy は CI で `-D warnings` を付けて実行されます。
- 現在確認済みのベースラインは Worker 146 テストと合格するデスクトップ 106 テストです。実録画/アーカイブの環境および性能テスト 4 件は、Windows デスクトップセッション、合法な録画またはアーカイブパス、経路固有の性能しきい値を必要とするため、引き続きオプトインです。
- フロントエンド契約チェックは現在、58 個の型付きコマンド、64 個のソースファイル、4 個の完全な組み込みロケールファイルを対象とし、Svelte は診断なしでビルドされます。
- `scripts/check.ps1` は、フォーマット、Worker とデスクトップのテスト/lint、フロントエンドビルド、fuzz コンパイル、生成される依存ライセンス一覧のための唯一のローカルエントリーポイントです。
- `scripts/build.ps1` は唯一のパッケージングエントリーポイントです。Windows の既定はバンドルプロファイルで、固定されたランタイムを明示的にインストールして検証します。`-Libmpv External` は libmpv を含まないパッケージを生成し、互換ランタイムをユーザーが提供することを求めます。Tauri の基本設定自体が暗黙にランタイムをバンドルすることはありません。
- 通常の CI 経路には、共有静的品質ゲート、3 プラットフォーム Rust テストマトリクス、fuzz ターゲットのコンパイル、依存関係監査という 4 つの集中したジョブがあります。週次スケジュールワークフローは各 fuzz ターゲットを上限 30 秒で実行し、プルリクエストではコンパイルのみの fuzz カバレッジを維持します。`cargo-deny` は Worker、デスクトップ、fuzz の各マニフェストに対し、コミット済みのライセンス/ソースポリシーを強制します。長時間の LGPL libmpv ビルドは手動で、プルリクエスト CI から分離されています。GitHub Ubuntu ランナー上で直接実行され、対応するソースアーカイブの横に完全なツール/パッケージ環境を記録します。
- `scripts/verify-repository.ps1` は生成/ダウンロードされた成果物、ネストしたリポジトリ、サイズ過大な追跡ファイル、リリースバージョンのずれを拒否します。`scripts/package-source.ps1` はクリーンな Git リビジョンからハッシュ指定のソースアーカイブを作成し、両経路とも一時リポジトリで実行済みです。
- GitHub issue とプルリクエストのテンプレートは、合法なサンプル境界、影響を受けるトランスポート経路、モデル不変条件、検証エビデンスを記録します。

## 一般公開の阻害事項

- 依存関係を更新するたびに、`THIRD_PARTY_NOTICES.md` と `third_party/versions.json` を同期させ続けてください。正確な libaribcaption/libmpv リビジョン、ハッシュ、ライセンス、ソース場所、動的置換手順は記録済みです。
- 大容量の Windows libmpv バイナリを Git に入れないでください。固定アーカイブと展開後のハッシュは `scripts/setup-libmpv.ps1` で検証され、Windows CI とパッケージングはその明示的なセットアップ手順を呼び出します。
- ベンダー化された libaribcaption のコミットとソーススナップショットのハッシュを同期させ続けてください。ネストした Git メタデータは削除済みであり、今後の更新はルートリポジトリへ入る前に `scripts/prepare-vendored-source.ps1` を通過しなければなりません。
- バンドル対象の厳密な Windows libmpv ビルドについて、永続的で完全な対応ソースアーカイブとビルドスクリプトをミラーしてください。該当する LGPL 本文、ビルド来歴、ハッシュ、置換機構は記録済みですが、上流 URL だけを最終リリース成果物とは見なしません。
- Rounded M+ 1m for ARIB の来歴/ライセンスファイルがフォントの横にあり、すべてのインストーラーとバイナリアーカイブに含まれるようにしてください。バンドルされたバイナリは SHA-256 により記録済み上流ファイルと一致しています。
- `CONTRIBUTING.md`、`SECURITY.md`、対応ツールチェーンポリシーは現在存在します。Windows Alpha 候補ワークフローは完全なパッケージゲートを実行し、一般公開リリースを作成せずにインストーラーハッシュを書き込みます。
- 行動規範に関する決定を記録してください。Signed Stable リリースには保護された署名 ID が必要ですが、ソース、ハッシュ、来歴、ライセンスの各ゲートを満たし、明示的に開示される Unsigned Windows Alpha には不要です。
- 実際の実装と一致しなくなった主張をアーキテクチャ文書から削除し、3 言語版すべてが同じ検証済みおよび実験的機能境界を記述するようにしてください。

## 推奨順序

1. 正確なタグとコミット、完全な成果物ハッシュ、未署名ビルド警告、通知、バンドルされた libmpv の対応ソース受領証を公開する、監査可能な Unsigned Windows Alpha パイプラインを作成します。
2. ソース選択、ネイティブプレビュー、動的放送メタデータ、マルチタスク制御、言語パック、出力計画、成果物公開について、パッケージ済み Windows のエンドツーエンド受け入れを実施します。ソース選択、一時停止したネイティブ動画、動的メタデータ、118 イベントのインデックス作成、最終アーカイブのタイムライン復旧は `bs4k_test_2.ts` で検証済みですが、残りのワークフローにはまだパッケージ受け入れが必要です。
3. 非公開の実放送互換性マトリクスを維持し、その結果だけを公開します。合法的に保有する録画の代わりに合成放送生成を追加してはならず、TLV/MMTP は明示的に実験扱いのままにしてください。
4. フロントエンドのテストフレームワークや RPC フレームワークを導入せず、純粋なフロントエンド動作と生成された Rust-to-TypeScript DTO 型に集中したテストを追加します。
5. バンドル対象の厳密な LGPL libmpv ビルドについて固定された完全な対応ソースパッケージを作成します。それが完了するまで、現在の開発 DLL は公開バイナリ配布を阻害します。
6. Cargo/npm の依存関係監査を有効に保ちます。libmpv の対応ソースゲートを通過した後にのみ未署名 Alpha を公開し、Signed Stable へ昇格する際には署名を別個の要件として追加します。
