# ResubWinny

> [!WARNING]
> This project is currently in the early alpha stage; availability cannot be guaranteed, and there may be breaking changes!

ResubWinny is a Windows application for extracting, inspecting, previewing, and converting subtitles from source video files containing a broad range of Japanese content. It has a modern user interface and can also be operated from the command line.

It can process ARIB subtitles in terrestrial digital television, BS/CS 2K, and some BS4K/8K recordings; preview video in real time; and, for playback in external players, produce subtitles that preserve positioning, color, font size, outline, Ruby (phonetic annotations), ARIB gaiji, DRCS glyphs, and accessibility indicators as far as possible. It can also discard special tags and output formats suitable for subsequent work or archiving.

The current convergence period focuses on subtitles from Japanese broadcast recordings. BD/DVD graphical-subtitle OCR, the plugin system, AI translation, and native preview on macOS/Linux have all been explicitly deferred and are outside the current roadmap and acceptance scope. For DRCS, work is limited to continuing improvements to the local hash → Unicode mapping; a general-purpose OCR system will not be expanded.

The project's current version is `v0.2.2-α` (source version `0.2.2-alpha.1`). It is still under development.

## Features

### Subtitle extraction and recognition

- Detects input formats from file content and does not rely on `.ts`, `.m2ts`, or `.mmts` extensions;
- Supports ARIB STD-B24 subtitles in 188-byte MPEG-TS;
- Supports 192-byte M2TS-style MPEG-TS, private PES, and strictly validated ARIB-TTML subtitles;
- Supports discovery and selection of multiple services and multiple subtitle tracks;
- Parses available broadcast networks, services, programs, and broadcast times from recordings and can query the corresponding state by playback position; it does not fabricate fields when corresponding SI/EIT/TOT evidence is absent;
- Strictly handles TTML encoded as UTF-8, UTF-16LE/BE, Shift_JIS, EUC-JP, and ISO-2022-JP;
- Provides structured diagnostics for corrupted, truncated, or unsupported input.

### Subtitle semantics and layout

- Preserves independent display times and overlap relationships for subtitle regions;
- Preserves position, font size, color, outline, opacity, character spacing, and writing direction;
- Recognizes and preserves the structured correspondence between Ruby and the annotated base text;
- Supports horizontal writing, basic vertical writing, continuous Ruby grouping, and vertical character-orientation handling;
- Recognizes ARIB special symbols, custom DRCS glyphs, and common accessibility indicators;
- Normalizes geometry from 2K, 4K, and 8K sources to a logical subtitle plane so subtitles retain similar viewer-visible proportions.

### Export and inspection

- Allows multiple output formats, including ASS, TTML, SRT, and WebVTT, to be selected at once;
- Allows separate decisions on whether to preserve position, color, Ruby, DRCS, ARIB gaiji, and accessibility indicators;
- Filters and marks special subtitle features in the subtitle event list;
- Provides project archives, raw PES/MMTP evidence, and DRCS reports;
- Supports pausing partway through, writes temporary `.part` files first, and emits complete files after success;
- The backend validates input and output paths to prevent subtitle output from overwriting the original recording.

### Desktop application

- Multilingual interface with built-in Simplified Chinese, Traditional Chinese, Japanese, and English;
- Supports light, dark, and system themes;
- Supports creating, queuing, pausing, resuming, and canceling multiple tasks, as well as history and diagnostics;
- Provides a subtitle event list, zoomable timeline, click/drag seeking, and a DRCS dictionary;
- On Windows, uses libmpv to render video natively and does not send video frames into the WebView;
- B24 subtitle planes and ARIB-TTML subtitle images are generated by the Rust backend and composited over the native preview.

## Input support status

| Input route | Status | Description |
| --- | --- | --- |
| 188-byte MPEG-TS + ARIB STD-B24 | Validated | Intended for terrestrial digital television and BS/CS 2K recordings |
| 192-byte M2TS-style MPEG-TS + private PES + ARIB-TTML | Validated | Covered by regression tests using the existing BS4K recording samples; applicability is determined by content detection |
| Private PES/TTML candidates in MPEG-TS | Bounded detection | Conversion occurs only after complete XML boundaries, declared encoding, and the TTML document all pass validation |
| Raw TLV/IP/UDP/MMTP | Experimental | Focused on detection, diagnostics, and raw evidence; complete `stpp`/TTML assets are processed only under strict conditions |
| Unknown or unsupported input | Explicitly rejected | Returns stable errors and detection evidence; does not guess the container or subtitle type |

Raw TLV/MMTP is not part of the currently validated general BS4K/8K support. File extensions are used only as hints in the file picker and cannot serve as evidence of the transport format.

## Output formats

| Format | Purpose and limitations |
| --- | --- |
| ASS | For subtitle authoring and common players; preserves position, color, font size, outline, and Ruby that ASS/libass can express, but cannot reproduce the semitransparent background rectangles behind subtitles |
| TTML | Preserves independent regions, timing, styles, Ruby, writing direction, DRCS references, and source information |
| SRT | Plain-text compatibility output; cannot express broadcast positioning, overlapping regions, Ruby layout, or DRCS graphics |
| WebVTT | Web-compatible text output; like SRT, it is a lossy format |
| Caption archive (`.caption.jsonl`) | Stores the unified subtitle model, region lifecycles, Ruby correspondence, and source information for paginated timelines and rerendering |
| Raw evidence | Stores source offsets, sequence numbers, time sources, and lossless PES/MMTP payloads |
| DRCS report/assets | Stores glyphs that cannot be mapped directly to Unicode, pixel assets, candidate mappings, and user selections |

## Technology stack

| Layer | Technology |
| --- | --- |
| Desktop frontend | Svelte 5, TypeScript, Vite, Lucide Svelte |
| Desktop application layer | Tauri 2, Rust 2024 Edition |
| Subtitle Worker | Rust, versioned JSONL protocol, streaming I/O |
| B24 decoding and rendering | libaribcaption, the project's own narrow C ABI, C++ bridge |
| Native video preview | libmpv render API; Windows WGL/OpenGL compositing |
| Subtitle model | `CaptionPlane -> RegionInterval -> exporters` |
| Persistence | Atomic JSON/JSONL files in the application data directory |
| Testing and quality | Cargo test, Clippy, Rustfmt, Svelte Check, cargo-fuzz, GitHub Actions |

The frontend only displays backend state and forwards typed requests. It does not read broadcast data, determine subtitle timing, calculate final subtitle layout, or process video frames. Media and subtitle capabilities are implemented in the Worker or Tauri backend before being integrated into the GUI; core operations available in the GUI should have a corresponding CLI, Worker, or backend API.

## Technical architecture

```text
Svelte 5 frontend
    | typed Tauri API / low-frequency events
    v
Tauri 2 Rust application service layer
    | task scheduling, persistence, native preview, Worker management
    v
arib-caption-worker
    | streaming detection, parsing, subtitle model, timeline, and export
    v
libaribcaption
    | the project's own narrow C ABI
    v
ARIB STD-B24 decoding and native subtitle plane
```

The Worker uses fixed-size streaming buffers and 64-bit file offsets. Under normal operation, memory usage should not grow linearly with file length as file size increases. For detailed responsibilities and interfaces, see the [Chinese architecture document](docs/architecture.zh-CN.md) and [backend interface contract](docs/backend-contract.md).

## Build environment

The complete desktop acceptance platform for the current Alpha is Windows 11 x86-64. Requirements:

- Rust `1.97.1` pinned by `rust-toolchain.toml`, including Rustfmt and Clippy;
- Node.js 22 LTS;
- npm 10 or 11;
- CMake;
- Visual Studio 2022 Build Tools, including the MSVC C/C++ toolchain and Windows SDK;
- Microsoft Edge WebView2 Runtime;
- 7-Zip, used to install the pinned Windows libmpv development package.

Worker and Tauri compilation checks and frontend builds run in Windows, macOS, and Linux CI; the product acceptance platform for native preview and installers remains Windows.

## Build instructions

Run all commands below from the repository root.

### 1. One-command build

```powershell
./scripts/build.ps1
```

This command installs locked frontend dependencies, downloads and verifies the pinned Windows libmpv, and builds the Worker, frontend, desktop application, and installer. On repeated runs, an already verified libmpv is reused directly. ResubWinny does not download or update playback components at runtime.

To generate only the executable, without an installer:

```powershell
./scripts/build.ps1 -Target Executable
```

To build a version without bundled libmpv:

```powershell
./scripts/build.ps1 -Libmpv External
```

This mode does not distribute libmpv, but real-time preview requires a compatible runtime supplied through `RESUBWINNY_LIBMPV`. Add `-Check` when the complete quality checks must also run. Local artifacts that bundle libmpv are for development and private testing only; before public release, a verified corresponding source package and receipt must still be provided for the exact same DLL.

### 2. Run complete quality checks

```powershell
./scripts/check.ps1
```

This script covers Worker and desktop backend tests, Clippy, Rustfmt, Svelte checks, the frontend/backend interface contract, fuzz target compilation, the license inventory, and third-party source verification.

### 3. Development run

Build the Worker first, then start the Tauri development application:

```powershell
cargo build -p arib-caption-worker
npm run tauri --prefix studio-tauri -- dev
```

To use another Worker, set `RESUBWINNY_WORKER` to the executable's absolute path.

### 4. Invoke underlying build commands directly

The base Tauri configuration does not require libmpv to be bundled, so the commands below are suitable for development and builds that use only an external runtime. To generate only the desktop executable:

```powershell
npm run tauri --prefix studio-tauri -- build --no-bundle
```

To generate a Tauri bundle without bundled libmpv:

```powershell
npm run tauri --prefix studio-tauri -- build
```

When an installed and hash-verified Windows libmpv must be bundled, use the unified build script or explicitly add the configuration:

```powershell
./scripts/setup-libmpv.ps1
npm run tauri --prefix studio-tauri -- build --config src-tauri/tauri.windows-libmpv.conf.json
```

Artifacts are located uniformly at:

```text
build/cargo/release/resubwinny-studio.exe
build/cargo/release/bundle/
```

Clean build artifacts:

```powershell
./scripts/clean.ps1
```

Add `-Dependencies` to delete `node_modules`; add `-DownloadedRuntimes` to delete explicitly installed libmpv development files; add `-TestOutputs` to delete local test output.

## Using the desktop application

1. Start `build/cargo/release/resubwinny-studio.exe`.
2. Select a recording on the home page. The application detects the container, services, and subtitle tracks from content and automatically prepares native preview; preview is paused by default and does not play automatically.
3. Open the task page to view broadcast services, subtitle tracks, the event list, and the timeline; program and broadcast times are displayed when the recording contains the corresponding broadcast tables and they are parsed successfully.
4. In the preview window, play, pause, seek backward or forward, drag the timeline, or adjust the volume. The subtitle timeline below can be zoomed, clicked, and dragged to seek.
5. In output settings, select one or more formats and choose whether to preserve position, color, Ruby, DRCS/ARIB gaiji, and accessibility indicators. The interface warns about content that the target format cannot express completely.
6. Select an output directory and start the export. Before export begins, the application does not create subtitle artifacts in the selected output directory.
7. Inspect results in the task log, diagnostics, and artifact list. When unmapped DRCS is encountered, view the original image in the DRCS dictionary and save a mapping.
8. Additional recordings can be added to form a multitask queue; the backend persists and schedules each task independently.

## CLI usage

The default Worker path is:

```text
build/cargo/release/arib-caption-worker.exe
```

All machine-readable events are written to `stdout`, and human-readable logs are written to `stderr`. All current CLI commands are listed below.

### `inspect`

Detects the input format, services, subtitle tracks, and candidate routes without exporting subtitles.

```text
arib-caption-worker.exe inspect <recording>
```

### `broadcast-at`

Queries the corresponding broadcast network, service, program, and broadcast time in MPEG-TS/M2TS by source-file byte offset. `service-id` uses decimal.

```text
arib-caption-worker.exe broadcast-at <recording> <byte_offset> [--service-id <id>]
```

### `decode-b24`

Discovers and sequentially decodes traditional B24 subtitle tracks, emitting progress and statistics events without creating subtitle files.

```text
arib-caption-worker.exe decode-b24 <recording>
```

### `convert`

Automatically detects the route from content and converts subtitles. If no output path is specified, the input filename is used by default with its extension changed to `.ass`.

```text
arib-caption-worker.exe convert <recording> [output] [options]
```

### `convert-b24`

Converts subtitles using only the traditional MPEG-TS/B24 route. Its arguments are the same as `convert`.

```text
arib-caption-worker.exe convert-b24 <recording> [output] [options]
```

`convert` and `convert-b24` support all of the following options:

| Option | Effect |
| --- | --- |
| `--ttml` | Also export TTML |
| `--srt` | Also export an SRT-compatible copy |
| `--webvtt` | Also export a WebVTT-compatible copy |
| `--archive` | Also export a caption archive |
| `--archive-only` | Publish only a caption archive; cannot be combined with other formats or `--no-ass` |
| `--raw` | Export raw PES/MMTP evidence for the route |
| `--no-ass` | Do not retain the default ASS output |
| `--drcs-report` | Generate a report when DRCS is found |
| `--drcs-map <json>` | Use DRCS user mappings from the specified JSON file |
| `--track-id <id>` | Select the subtitle PID/asset; accepts decimal or `0x` hexadecimal |
| `--drop-position` | Do not preserve subtitle position |
| `--drop-color` | Do not preserve color |
| `--drop-ruby` | Do not preserve Ruby |
| `--drop-drcs` | Do not preserve DRCS glyphs |
| `--drop-gaiji` | Do not preserve special ARIB gaiji |
| `--drop-accessibility` | Do not preserve accessibility indicators |
| `--overwrite` | Allow existing output artifacts to be overwritten; overwriting the input recording remains prohibited |

Examples:

```text
arib-caption-worker.exe convert recording.ts output.ass --ttml --archive --raw --drcs-report
arib-caption-worker.exe convert recording.m2ts output.ass --track-id 0x120 --srt --webvtt
arib-caption-worker.exe convert-b24 recording.ts output.ass --drop-position --drop-accessibility
arib-caption-worker.exe convert recording.ts output.caption.jsonl --archive-only
```

During conversion, cooperative control messages can be sent line by line through `stdin`:

```json
{"type":"pause"}
{"type":"resume"}
{"type":"cancel","keepCheckpoint":true}
```

### `render-at`

Reads the subtitle-region snapshot at the specified millisecond time from a caption archive and outputs it as JSONL events.

```text
arib-caption-worker.exe render-at <archive.caption.jsonl> <time_ms>
```

### `dump-tlv`

Experimental extraction of raw TLV/MMTP evidence. If output is not specified, `.caption.mmtp.jsonl` is generated by default.

```text
arib-caption-worker.exe dump-tlv <input> [output.caption.mmtp.jsonl] [--overwrite]
```

This command outputs only complete closed-caption payloads from discovered `stpp` assets and preserves TLV offsets, MMTP/MPU sequence numbers, raw NTP, and lossless bytes. It does not misrepresent NTP as PTS or guess that unknown assets are subtitles.

## Development and validation

The Worker can be built and tested independently:

```powershell
cargo test -p arib-caption-worker
cargo build -p arib-caption-worker --release
```

Changes involving transport, protocols, the subtitle model, timeline, rendering, or exporters require corresponding regression tests. Large lawful recording samples that cannot be redistributed are retained only locally and participate in optional long-sample validation through `ARIB_FIXTURE_DIR`. For details, see the [corpus and regression document](docs/corpus.md).

Before contributing, read the [contribution guide](CONTRIBUTING.md), [Chinese architecture document](docs/architecture.zh-CN.md), [backend interface contract](docs/backend-contract.md), [toolchain policy](docs/toolchain-policy.md), and [maintainability notes](docs/maintainability.md).

## Limitations

- Raw TLV/MMTP for BS4K/8K is an isolated experimental capability and is not part of validated general BS4K/8K support;
- 192-byte M2TS support describes only the packet-encapsulation route and does not imply complete support for BDMV/BDAV directories, playlists, CAS, or vendor-private recording-management information;
- ResubWinny is not a recording manager, live broadcast receiver, CAS decryption tool, or complete EPG browser;
- SRT and WebVTT cannot accurately express overlapping regions, broadcast positioning, Ruby layout, DRCS graphics, and all ARIB timing semantics;
- The B62/ARIB-TTML rules corresponding to BS4K/8K signals remain under study.

Source releases and Windows binary releases use different thresholds; for specific items, see the [release checklist](docs/release-checklist.md).

## Afterword

To me, Japanese television culture has a unique charm. Even setting aside the content broadcast on television, its network system and technical details are equally fascinating. Others may not understand this obsession of mine, but what if I told you that in the country where I live, television signals have only a single audio track (without even the bilingual ability) and video? When I first encountered Japanese digital television and saw that it had subtitles that could be turned on and off and interactive data broadcasting, I was overwhelmed by the novelty of it all. I recall that, when I was a child, one day the subtitles burned into the picture suddenly disappeared; I cried that I could no longer understand it, causing my parents to add subscriptions to several children's channels. It makes me feel that the only thing worth discussing about the television culture of the country where I live is its own history; beyond that, there is nothing but barrenness upon barrenness.

But Japanese television signals are full of home-grown wheels and traces of the “Galápagos syndrome.” Once ordinary people leave that specially provisioned viewing environment, it becomes difficult for them to see the signals' true form. Thanks to developers' enthusiasm over many years, signal sources have gradually become parseable, and watching television freely is no longer an empty phrase. Yet ordinary people still lack convenient and “comprehensible” tools for crossing the technical threshold. Reading text is the beginning of understanding, and subtitles are the medium that carries text, so I wanted to start with subtitles and make a tool.

Returning to the name ResubWinny: the original Winny was P2P file-sharing software released in 2002. Its widespread use was accompanied by the distribution of copyrighted and inappropriate content and was regarded as a social problem, yet the software's author was prosecuted because of users' actions. In 2023, a film of the same name based on the incident was released; its title at the Shanghai International Film Festival was “Developer is Guilty.”

Resub represents the reworking of subtitles, while Winny pays tribute to the name's inventor, Isamu Kaneko, a.k.a. 47氏, and follows a basic principle of common sense:

**Developing general-purpose technology is not a crime; it is part of freedom of expression.**

This project does not involve P2P networks, file sharing, media discovery, or content distribution. It is an open-source tool. Tools that read media formats, recover subtitles, perform OCR, or convert data do not themselves constitute infringement. Their legality and ethics depend on how they are used, not merely on what they are technically capable of doing.

The desire to create ResubWinny arose because too much knowledge about processing Japanese media is trapped in hard-to-organize 2ch posts, abandoned Windows utilities, official ARIB documents whose visibility is divided by class, and software that provides no source code. This knowledge should be more open, auditable, portable, and preservable. Existing tools also often discourage beginners through unclear guidance and barriers to understanding.

Therefore, this project is not intended to recreate the original Winny. It is a declaration: **developers should have the freedom to build lawful tools, users should have the freedom to understand media they own, technology itself should be simple and easy to use, and knowledge should not disappear because of fear, prosecution, or closed code.**
